# AEGIS-2026-001: identifiers split by a line break or set in square brackets could pass the privacy release

| | |
|---|---|
| Advisory | AEGIS-2026-001 |
| Disclosed | 2026-10-03 |
| Affected | every version with recognizer pack `aegis-custom-strict-v1` or `-v2`: commits from 2026-07-17 up to and including the archived release v0.1.0 |
| Fixed in | 0.1.1 (recognizer pack `aegis-custom-strict-v3`) |
| Check | `aegisqda audit <run-root>` (read-only, prints no source text) |
| Exposure | limited: AegisQDA 0.1.x only accepts material declared synthetic |

Kurzfassung auf Deutsch und résumé en français: [below](#kurzfassung-deutsch).

## Summary

AegisQDA's detector silently discarded three kinds of identifier before the human
review. Because the review shows only what the detector found, and the second
scan after replacement used the same detector, the affected text was released
with the state `PRIVACY_RELEASED`:

1. **Mentions that cross a line break.** Subtitle files usually wrap a cue over
   two lines. When a name falls on the wrap, the spaCy models return it as one
   entity spanning the line break (`Maria\nGonzalez`). The detector dropped every
   finding that did not fit into a single line. Reproduced with the pinned models
   `de_core_news_lg`, `fr_core_news_lg` and `en_core_web_lg` 3.8.0, for example
   `Anna\nSchneider`, `Marie\nDupont`, `Maria\nGonzalez`, `New\nYork` and
   `Deutschen\nRoten Kreuz`. Hard-wrapped TXT transcripts are affected the same way.
2. **Values in square brackets.** Any finding whose exact text started with `[`
   and ended with `]` was skipped, so `My name is [Jane Example] and I live …`
   or `Ich heiße [Anna Schneider] und wohne …` was released unchanged.
3. **Unicode line separators.** U+2028, U+2029, U+0085, form feed, vertical tab
   and U+001C–U+001E split lines like case 1 and caused the same drop.

## Impact

Released transcripts (`transformed.srt` / `transformed.txt`) produced by an
affected version can contain names, places or organisations in clear text.

Downstream, DigQDA's segmenter joins the lines of a cue before analysis. In our
reproduction, AegisQDA's post-analysis scan flagged the line-wrapped names in
that segment output, which blocks `analyze`; it did not flag the bracketed names.
This is a second line of defence, not a guarantee. DigQDA results never leave the
protected state `DOWNSTREAM_REVIEW_REQUIRED` in any version.

## Who is affected

AegisQDA 0.1.x is a synthetic-only MVP. Real-data processing is disabled in code:
`scan` requires `--synthetic`, and the configuration pins
`real_data_enabled: false`. **If you only processed synthetic material, no
personal data was exposed.** If you processed real material despite this
boundary, treat every privacy release made with an affected version as not
de-identified.

## What to do

1. Update to 0.1.1.
2. Run `aegisqda audit <run-root>` for every run root you used (the default is
   `/private/tmp/aegisqda-runs`). It reads the runs, writes nothing, and reports
   one verdict per run:
   - `AFFECTED`: the current detector finds identifiers in released text, or
     the released text no longer passes the parser. Treat this transcript and
     every copy of it as not de-identified: retrieve or delete copies you
     shared, inform your data protection officer if real data was involved, and
     scan the source again.
   - `RESCAN_REQUIRED`: an unreleased run from an affected version. Scan the
     source again; the old run cannot continue.
   - `NO_FINDINGS_UNDER_CURRENT_DETECTOR`: a released run from an affected
     version in which the current detector finds nothing unresolved. There is
     no evidence of this defect, but the run cannot be analyzed; scan again to
     continue.
   - `CURRENT`: scanned with the fixed recognizer pack; nothing to do.
   - `INVALID`: the run's artifacts are missing or fail their integrity check.
3. Runs from the affected recognizer packs stop with a message that names this
   advisory if you try to review, transform or analyze them. This is
   intentional.

The audit shows what the current detector finds. It is not a proof of anonymity,
and human review remains required.

## What changed in 0.1.1

- Findings that cross a line break are kept and reviewed as one mention. The
  mention gets one placeholder on its first line, shared with the same name
  elsewhere in the document (`Maria\nGonzalez` and `Maria Gonzalez` both become
  `[PERSON_001]`). The rest is removed from the next line, or becomes `[…]` when
  the line would otherwise be empty, so SRT cues and line counts stay intact.
- Only the exact placeholder shape AegisQDA writes (`[PERSON_001]`) is skipped;
  other bracketed text is scanned.
- Unicode line separators other than LF/CRLF are rejected when the source is read.
- Recognizer packs v1 and v2 are revoked in code, and `aegisqda audit` was added.
- New regression tests pin all three cases.

## Timeline

- 2026-07-17: the line filter and the bracket skip were introduced with
  recognizer pack v1.
- 2026-08-08: release v0.1.0 archived on Zenodo (recognizer pack v2, affected).
- 2026-09-30: found in a code review and reproduced
  end to end with the pinned spaCy models; first fix published on a public branch.
- 2026-10-03: run gate, audit and one placeholder per mention completed; advisory
  disclosed.

## Lessons for other de-identification pipelines

The first case is not specific to AegisQDA. Any pipeline that runs NER over a
whole transcript but filters, maps or replaces findings line by line can lose
entities that cross a line break. Subtitle formats, hard-wrapped transcripts and
OCR output make this common. The regression tests in
`tests/test_ner_integration.py` contain small synthetic cases you can reuse to
check your own tool.

## Kurzfassung (Deutsch)

**Was ist passiert?** Bis einschließlich Version 0.1.0 hat der Detektor von
AegisQDA drei Arten von Identifikatoren vor der menschlichen Prüfung stillschweigend
verworfen: Namen, die über einen Zeilenumbruch gehen (etwa ein Name, der in einem
zweizeiligen Untertitel umbricht), Werte in eckigen Klammern wie `[Anna Schneider]`
und Text, der durch seltene Unicode-Zeilentrenner getrennt ist. Weil die Prüfung
nur Gefundenes zeigt und der zweite Scan denselben Detektor nutzt, wurden solche
Stellen mit dem Status `PRIVACY_RELEASED` im Klartext freigegeben.

**Bin ich betroffen?** AegisQDA 0.1.x verarbeitet nur als synthetisch
deklariertes Material; echte Daten sind im Code gesperrt. Wer nur synthetisches
Material verarbeitet hat, hat keine personenbezogenen Daten offengelegt. Wer
trotzdem echte Daten verarbeitet hat, sollte jede Freigabe einer betroffenen
Version als nicht pseudonymisiert behandeln.

**Was tun?** Auf 0.1.1 aktualisieren und `aegisqda audit <Lauf-Verzeichnis>`
ausführen. Der Befehl liest nur, schreibt nichts und gibt keinen Quelltext aus. Bei
`AFFECTED`: das freigegebene Transkript samt Kopien als nicht pseudonymisiert
behandeln, weitergegebene Kopien zurückholen oder löschen, bei echten Daten die
bzw. den Datenschutzbeauftragten informieren und die Quelle neu scannen. Bei
`RESCAN_REQUIRED` die Quelle neu scannen; alte Läufe lassen sich nicht fortsetzen.

**Was ändert sich?** Ein umbrochener Name wird als eine Nennung geprüft und durch
genau einen Platzhalter ersetzt, derselbe wie für den Namen an anderer Stelle im
Dokument. Die Struktur von Untertiteln und Zeilen bleibt erhalten.

## Résumé (français)

Jusqu'à la version 0.1.0 incluse, le détecteur d'AegisQDA écartait sans le signaler
les noms coupés par un retour à la ligne (par exemple dans un sous-titre sur deux
lignes), les valeurs entre crochets comme `[Marie Dupont]` et le texte séparé par
des séparateurs de ligne Unicode. Ces passages pouvaient être publiés en clair avec
le statut `PRIVACY_RELEASED`. AegisQDA 0.1.x n'accepte que des données déclarées
synthétiques ; si vous n'avez traité que de telles données, aucune donnée
personnelle n'a été exposée. Mettez à jour vers 0.1.1 et lancez
`aegisqda audit <répertoire des exécutions>` (lecture seule, aucun texte source
affiché) ; pour tout résultat `AFFECTED`, considérez la transcription publiée et
ses copies comme non pseudonymisées et relancez l'analyse de la source.
